# Database — Drizzle ORM 1.0 (rc) + Postgres

Drizzle 1.0 release candidate with the `postgres` driver. It differs from the 0.x most
examples show: relations are defined once with `defineRelations`, columns come from
`getColumns`, and `drizzle-kit` writes one folder per migration.

## Files in `src/drizzle/`

| File                 | Holds                                                                          |
| -------------------- | ------------------------------------------------------------------------------ |
| `index.ts`           | `db` (the client) and `schema`. Import both from `@/drizzle`                   |
| `schema/*.schema.ts` | Tables, one file per domain (`jobs.schema.ts`)                                 |
| `relations.ts`       | `schema` (every table, frozen) and `relations` (`defineRelations`)             |
| `table-columns.ts`   | `getColumns(table)` per table: `jobColumns`, `assetColumns`, `jobInputColumns` |
| `types.ts`           | Row types: `Job`, `JobInsertValues`, `Asset`, …                                |
| `utils.ts`           | `sharedTimestampColumns`, `withPagination`, `toPagination`, `lastPageOf`       |
| `migrations/`        | Generated SQL. Never edit by hand                                              |

## Tables

| Table        | One row is…                                                                            |
| ------------ | -------------------------------------------------------------------------------------- |
| `jobs`       | One generation request: `kind`, `status`, `prompt`, `params` (jsonb), `error`, timings |
| `assets`     | One media file on disk: an upload (`job_id` null) or something a job made              |
| `job_inputs` | One reference image of a job, in order. An asset can feed many jobs                    |

Deleting a job cascades to its assets and inputs; deleting an asset cascades to the
`job_inputs` that point at it.

## Table conventions

```ts
export const assets = pgTable.withRLS(
  "assets",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    jobId: uuid("job_id").references(() => jobs.id, { onDelete: "cascade" }),
    kind: varchar("kind", { length: 20 }).notNull().$type<Media.AssetKind>(),
    isFavorite: boolean("is_favorite").notNull().default(false),
    ...sharedTimestampColumns
  },
  (self) => [
    uniqueIndex("assets_root_path_index").on(self.root, self.path),
    index("assets_role_created_at_index").on(self.role, self.createdAt.desc())
  ]
)
```

- `pgTable.withRLS`, plural snake_case table names, a `uuid` primary key generated by
  Postgres.
- camelCase in TS, snake_case in SQL. Booleans start with `is` / `has` / `should`.
- Every table spreads `sharedTimestampColumns` (`createdAt`, `updatedAt`), `timestamptz`.
- A fixed set of values is a `varchar` typed with `.$type<Media.X>()`, not a Postgres
  enum: the union lives in `src/types/schema.d.ts`, the list in `@/constants`, and adding
  a value needs no migration.
- `jsonb` columns are typed the same way
  (`params: jsonb("params").$type<Media.JobParams>()`). The union is discriminated on
  `kind`, so narrow before reading (`if (params.kind === "video")`).
- Index what the app filters and sorts by, and name it `<table>_<columns>_index`.
- A comment above each table says what one row is.

## Queries

Readers live in `actions/<domain>/read.ts` and return view models, not rows.

```ts
const assetViewColumns = pick(assetColumns, [
  "id",
  "jobId",
  "kind",
  "role",
  "path",
  "width",
  "height"
])

const rows = await db
  .select({ asset: assetViewColumns, job: pick(jobColumns, ["id", "kind", "prompt"]) })
  .from(schema.assets)
  .innerJoin(schema.jobs, eq(schema.jobs.id, schema.assets.jobId))
  .where(filter)
  .orderBy(desc(schema.assets.createdAt))
```

- Reach tables through `schema.x` from `@/drizzle`; select only the columns the view needs
  with `pick` / `omit` (es-toolkit) over `@/drizzle/table-columns`.
- Never send a file path to the browser. Readers map rows to `AssetView`, whose `url` is
  `/api/media/<id>`.
- Timestamps cross to the client as numbers (`createdAt.getTime()`).
- One query per need, run together with `Promise.all`; avoid a query per row (load the
  related rows with `inArray` and group them, as `readRecentJobs` does).
- Lists that can grow are paginated: count with the same filter, clamp the page with
  `lastPageOf`, fetch with `withPagination`, return `toPagination(…)` (`Pagination<T>`).
- A status change that can race is a **conditional update**:
  `.where(and(eq(jobs.id, id), eq(jobs.status, "queued"))).returning(…)`, then act on
  whether a row came back.
- Scripts and the worker must close the client when done: `await db.$client.end()`.

## Migrations

```sh
bun run drizzle:generate   # after changing a schema file: writes src/drizzle/migrations/<timestamp>_<name>/
bun run drizzle:migrate    # applies what hasn't been applied
```

- Change the schema file, generate, read the SQL it wrote, then migrate.
- Commit the migration folder with the schema change. Don't edit or delete an applied
  migration; write a new one.
- `drizzle:push` skips migrations and is only for throwaway experiments on an empty
  database.
- The connection comes from `DATABASE_URL` in `@/constants/env`, built from the `DB_*`
  variables.
