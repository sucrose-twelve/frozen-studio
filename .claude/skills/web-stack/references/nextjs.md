# Next.js 16 in this project

Next.js 16.4, App Router, Turbopack, `cacheComponents: true`. The docs that match the
installed version are in `node_modules/next/dist/docs/01-app/`; read the relevant page
before using an API you haven't used here yet.

## Things that changed and trip people up

- `params` and `searchParams` are **promises**: `await` them. Pages take
  `NextSearchParams` / `NextParams<…>` (global types), Route Handlers take
  `ctx: RouteContext<"/api/media/[id]">` (generated by `bunx next typegen`).
- `error.tsx` receives `{ error: unknown, retry }` — `retry()` re-fetches and re-renders
  the segment. Narrow `error` with `instanceof Error` before reading it.
- `middleware.ts` is `proxy.ts` now. This app has neither.
- `next dev` writes to `.next/dev`, `next build` to `.next`. `bun run build` deletes
  `.next` entirely, so stop the dev server first.
- `agentRules: false` in `next.config.ts`: Next.js doesn't generate `AGENTS.md` /
  `CLAUDE.md`. Agent instructions live in `.claude/`.
- `devIndicators.position` is `bottom-right`, away from the studio's submit bar.

## Rendering: plain SSR, nothing cached

Everything the app shows changes from one second to the next (a job starts, a result
lands), and there is one user. So:

- Pages are Server Components that read straight from Postgres on every request. No
  `"use cache"`, no `cacheTag`, no `revalidate*`.
- Every page and the root layout export `instant = false`, which opts the route out of
  Cache Components' instant-navigation checks: the page may wait for its data instead of
  needing a `<Suspense>` shell.
- No `loading.tsx`, no skeletons, no `<Suspense>` around data. The queries are fast; a
  transition (`useTransition`) covers the moment a navigation takes.
- Independent queries run in `Promise.all`.

```tsx
export const instant = false

export default async function Studio({ searchParams }: NextSearchParams) {
  const query = queryValidator.parse(await searchParams)

  const [recent, selected] = await Promise.all([
    readRecentJobs(),
    jobId ? readJob(jobId) : null
  ])
  …
}
```

Live data reaches the page two ways, and both are already wired:

1. **The event stream.** `JobEvents` (in the studio layout) holds an `EventSource` on
   `/api/events` and feeds the zustand store: engine status, job status, progress.
2. **`router.refresh()`.** When a job reaches an end state, `JobEvents` refreshes the
   route so the server renders the finished job. A Server Action that changes what a page
   shows is followed by `showJob(…)` or `router.refresh()` on the client.

So a component usually has both: a prop from the server and a live value from the store,
and the live one wins (`const status = live?.status ?? job.status`).

## Server Actions

`"use server"` files in `src/actions/<domain>/`. Mutations only: `create.ts`, `update.ts`,
`delete.ts`. Readers in `read.ts` are plain async functions called by Server Components,
not actions.

```ts
"use server"

export async function cancelJob(input: unknown) {
  const parsed = jobIdValidator.safeParse(input)
  if (!parsed.success) return { ok: false as const, message: "Invalid job" }
  …
  return { ok: true as const }
}
```

- Take `input: unknown` and parse it with Zod. The form already validated, but the action
  is a public endpoint.
- Return `{ ok: true as const, … }` or `{ ok: false as const, message }`. Don't throw for
  things the user can cause.
- An action that queues work writes the `jobs` row first and pushes to Redis second, then
  publishes an event (see [engine.md](engine.md#queueing-a-job)).
- Actions never call ComfyUI.

## Route Handlers (`app/api/**/route.ts`)

Only for responses that aren't UI:

| Route             | What it does                                                                                               |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| `/api/events`     | Server-Sent Events: relays the Redis channel the worker publishes on. One Redis subscription per open page |
| `/api/media/[id]` | Serves an asset's file by id, with HTTP Range for video. `?download` sends it as an attachment             |
| `/api/uploads`    | `POST` multipart: stores a reference image (PNG) in ComfyUI's input directory and returns its asset        |

- Validate params with Zod and answer bad input with a bare status (`404`), no body.
- Streams stop reading when the request is aborted (`request.signal`).
- Files are addressed by **asset id**, never by a path from the client. `assetFilePath()`
  (`@/libs/media`) resolves the stored path and refuses one that leaves its root.

## Special files

- `app/layout.tsx` — `<html class='dark' data-theme='dark'>`, the fonts, `NuqsAdapter`,
  `Toaster`.
- `app/(studio)/layout.tsx` — reads the engine status, mounts the store, the event stream
  and the header.
- `app/error.tsx`, `app/not-found.tsx` — full-page fallbacks in the app's look.

## Navigation

- `next/link` for links. Selecting a job is URL state, changed through `useStudioQuery`
  (`showJob`), not `router.push`.
- A link into the studio from elsewhere spells the params out:
  `/?job=<id>&mode=<kind>&asset=<id>`.

## The security notice

Next.js checks the installed version against npm's advisories. On an affected version, the
first `next dev` or `next build` after `.next` is created stops with exit code 1 and an
upgrade notice; the same command run again continues with a warning. Since `bun run build`
deletes `.next` every time, it then stops every time until Next.js is upgraded (this
happened on 16.4.3; the owner moved to 16.4.6). Tell the owner and let them decide on the
upgrade; don't run `next upgrade` unasked.
